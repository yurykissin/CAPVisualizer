    Conditional Access sign-in log queries

    CAPVisualizer does not download sign-in logs. It reads policy configuration only. The queries below answer the questions configuration alone cannot: which policies actually fired, and which sign-ins no policy protected. Run them in the Log Analytics workspace, Microsoft Sentinel workspace, or Microsoft Sentinel data lake that receives the tenant's Entra sign-in logs.

    Before you run these

    1. Confirm sign-in logs reach a workspace. Entra sign-in logs are only queryable here if a diagnostic setting exports them. Check Entra ID → Diagnostic settings for a rule sending the SignInLogs category (and, if you need them, NonInteractiveUserSignInLogs) to a workspace. Without it these tables are empty and every result below is misleading rather than merely absent.
    2. Get read access to that workspace. The Log Analytics Reader Azure role on the workspace is enough. This is Azure RBAC on the resource, separate from the Entra permissions used to produce this report, and is often approved by a different owner.
    3. Open the right editor. Azure portal → Log Analytics workspaces → select the workspace → Logs. In Microsoft Sentinel, use Logs in the Sentinel workspace.
    4. Set the observation period in the time-range picker, above the query editor. Thirty days is a reasonable screening window; ninety is better before retiring a policy. Retention limits what you can ask for: the tables only hold what the workspace was configured to keep.
    5. Paste one query and run it. Use the copy buttons below, then Run. Export results with Export → CSV if you are attaching them to a review.
    Do not add a TimeGenerated filter. Every query below deliberately omits one. Basic, Auxiliary, Bronze, federated, and data lake tables require the time range to come from the query interface, and adding | where TimeGenerated > ago(30d) fails there with "Bronze Logs table query is missing time range". Use the picker instead. Filtering is what is restricted, so min() and max() of TimeGenerated inside summarize remain safe.

    1. Which policies are actually used

    One row per policy. Use it to screen for retirement candidates before acting on the consolidation findings in this report.

    Policy usage, per policy
    Table: SigninLogs
    SigninLogs
| mv-expand Policy = ConditionalAccessPolicies
| extend
    PolicyId = tostring(Policy.id),
    PolicyName = tostring(Policy.displayName),
    Result = tostring(Policy.result)
| where isnotempty(PolicyId)
| summarize
    Evaluated = count(),
    Success = countif(Result in ("success", "reportOnlySuccess")),
    Failure = countif(Result in ("failure", "reportOnlyFailure")),
    UserActionRequired = countif(Result == "reportOnlyInterrupted"),
    NotApplied = countif(Result in ("notApplied", "reportOnlyNotApplied")),
    AppliedUsers = dcountif(UserId, Result in (
        "success",
        "failure",
        "reportOnlySuccess",
        "reportOnlyFailure",
        "reportOnlyInterrupted"
    )),
    FirstSeen = min(TimeGenerated),
    LastSeen = max(TimeGenerated)
    by PolicyName, PolicyId
| extend Applied = Success + Failure + UserActionRequired
| extend AppliedPercent = round(100.0 * Applied / Evaluated, 2)
| project
    PolicyName,
    PolicyId,
    Evaluated,
    Applied,
    AppliedPercent,
    AppliedUsers,
    Success,
    Failure,
    UserActionRequired,
    NotApplied,
    FirstSeen,
    LastSeen
| order by Applied asc, NotApplied desc, PolicyName asc
    Interpretation. Success includes enforced and report-only success. Failure includes enforced and report-only failure. User action required is the report-only interrupted result. Applied is the sum of those three categories. Not applied means the policy was evaluated but its assignments or conditions did not match that sign-in. A zero Applied count means no observed impact during the selected period, not proof that the policy is safe to remove: break-glass, seasonal, and incident-response policies are expected to sit at zero.

    For retirement screening, AppliedUsers is the useful extra signal: it prevents a frequently signing-in user from making a narrowly used policy look broadly adopted. App, client, location, device, and risk breakdowns are better used during a follow-up investigation than in the first unused-policy screening query.

    2. Sign-ins where no policy applied at all

    The inverse view: not "is this policy dead" but "was this sign-in unprotected". Every row is traffic that Conditional Access evaluated and left ungoverned.

    Coverage gap: no policy applied
    Table: SigninLogs
    SigninLogs
| extend CAPs = iff(array_length(ConditionalAccessPolicies) == 0,
                    dynamic([{"result": "none"}]), ConditionalAccessPolicies)
| mv-apply Policy = CAPs on (
    summarize AppliedCount = countif(tostring(Policy.result) in ("success", "failure"))
)
| where AppliedCount == 0
| summarize
    Signins = count(),
    Apps = dcount(AppDisplayName),
    FirstSeen = min(TimeGenerated),
    LastSeen = max(TimeGenerated)
    by UserPrincipalName, AppDisplayName, ConditionalAccessStatus
| order by Signins desc
    Why the iff is there. When no policy is evaluated at all, ConditionalAccessPolicies is an empty array, and mv-apply and mv-expand silently drop those rows. Those are exactly the sign-ins this query exists to find, so the empty array is replaced with a placeholder before expansion. A query written without it reports a smaller gap than the tenant really has. Report-only results are excluded from AppliedCount on purpose: a report-only match enforces nothing.

    3. Sign-ins where no policy required MFA

    Narrower and usually more actionable: the sign-in may have matched a policy, but none that imposed a multifactor grant.

    Coverage gap: no MFA grant applied
    Table: SigninLogs
    SigninLogs
| where ResultType == 0
| extend CAPs = iff(array_length(ConditionalAccessPolicies) == 0,
                    dynamic([{"result": "none"}]), ConditionalAccessPolicies)
| mv-apply Policy = CAPs on (
    summarize MfaApplied = countif(
        tostring(Policy.result) in ("success", "failure")
        and (tostring(Policy.enforcedGrantControls) has "mfa"
          or tostring(Policy.enforcedGrantControls) has "multifactor"))
)
| where MfaApplied == 0
| summarize
    Signins = count(),
    LastSeen = max(TimeGenerated)
    by UserPrincipalName, AppDisplayName, AuthenticationRequirement,
       ClientAppUsed, IPAddress
| order by Signins desc
    Read AuthenticationRequirement before concluding anything. This query finds sign-ins no Conditional Access policy required MFA for. It does not mean MFA never happened: per-user MFA, security defaults, or a token that already carried a multifactor claim can all satisfy MFA without a policy grant. Rows showing singleFactorAuthentication are the genuine exposure. Add | where AuthenticationRequirement == "singleFactorAuthentication" to isolate them. ResultType == 0 limits the result to successful sign-ins, so failed attempts do not inflate the count.

    Scope and limitations

    • Interactive sign-ins only. SigninLogs excludes non-interactive, service principal, and managed identity activity. Union AADNonInteractiveUserSignInLogs for a fuller picture, but expect a much larger result set.
    • Absence of evidence. These queries describe the observation window only. A policy or gap outside it is invisible here.
    • Personal data. Queries 2 and 3 return user principal names and IP addresses. They are deliberately not part of the CAPVisualizer safe export, which stays name-free. Handle their output under the tenant's own data rules.
